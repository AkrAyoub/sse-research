# R21 — Report-grounded, resource-constrained SSE network and adversarial test plan

**Date:** 2026-11-19. **Status:** design and source security gates only, not evidence of a deployed public chain or deployed dashboard. **User resource limit:** provisionable university/cloud VMs are limited; the *only* non-VM external device currently available for joining is the operator's laptop. No exact usable VM count, RAM/disk budget or public ingress has been supplied for the final experiment; don't invent these.

The user's six-page paper *Settlement-Sufficient Evidence for Trustless Inter-Cloud SLA Enforcement* is the **scientific reference, not a hard number-of-nodes specification**. The historical source/code in the paper is not automatically the current PR.

## Preserve what the paper actually establishes

- **Section III.C, Eq. (1)–(4):** evidence `E` defines admissible contractual histories `H(E)`. For funded obligation `V` and provider entitlement `F(H)`, compute `L(E)=min(F(H))`, `U(E)=max(F(H))`, guaranteed provider `P=L(E)`, guaranteed consumer refund `C=V-U(E)`, unresolved escrow `X=U(E)-L(E)`. Preserve `P+C+X=V` and monotonic credited lower/upper bounds. A signed monitor observation is **not proof the off-chain event really occurred**; evidence soundness requires the actual history remain admissible.
- **Section III.E, Eq. (5):** exposure-aware admission: existing unresolved monetary exposure plus worst-case additional exposure for next epoch must not exceed the lease budget. Do not admit new obligations by assuming a disputed event was successful.
- **Section III.B:** threat model explicitly includes dishonest consumer/provider, missing/contradictory monitor reports, collusion and common-control Sybils, replay/reorder, delayed/lost messages. For `n` selected monitors, outcome quorum `q`, assumed Byzantine members `b`: `2q-n>b` for honest intersection; `q<=n-b` for availability under the fault assumption. The report's 4/3 example assumed `b=1`. It does **not** make four permanent monitors mandatory, does not prove physical independence or exonerate a fraudulent monitor quorum.
- **Section IV:** the reported Anvil and fixed witness prototype is **local contractual verification**, and the target distributed/cloud components are explicitly separate future extension. Figures 2–5 illustrate the desired contract boundary, workload/evidence flow, monitoring and conservative settlement—not evidence that an independently administered public network already ran.
- **Section II:** resource trading, incentive programs, monitoring schemes and quorum mechanics are related infrastructure, not SSE's standalone research novelty. The contribution is guaranteed payment under incomplete/contradictory evidence and safe continuation.

## Practical lab given finite VMs and only one non-VM external laptop

The **live network code must be role-count-open and adapt to arrivals/leaves**, while the **observed evaluation** has a finite honest resource budget and can prove only what was actually exercised:

| Stage | Machines actually needed | Experiment | What it can and CANNOT prove |
|---|---|---|---|
| A — private-safe client/genesis | One authorized VM | New independently generated chain31340 EL+CL genesis/config, real Besu+Lighthouse block/attestation startup; hash-pinned artifacts and genuine node metrics | Genuine native client operation, **NOT distributed independent operators or Internet P2P** |
| B — external peer onboarding | One configured VM with observed reachable P2P ingress + user's single laptop on a separate Internet path | Laptop independently obtains public genesis, syncs by actual EL+CL P2P, observes chain head/finality, fails/rejoins or changes access network | Real heterogeneous host/client/P2P connectivity, **NOT independent administrative ownership** because operator controls both |
| C — real role integration | Only actual available VM/laptop participants; roles may coexist on devices | Real consumer request, actual provider CPU/memory work, genuine monitor observations, signed receipts, chain-locked escrow; log all physical host and role co-location | True resource consumption and interhost traffic, **NOT independence of monitor witnesses if same owner/host controls them** |
| D — resilience/adversarial trials | Reuse actual machines and explicit disposable local roles; no invented hosts | Actual network drop/partition, restarted P2P peers, malicious or invalid signed messages, attempted unauthorized dashboard writes, replay, bad endpoints, resource exhaustion, protected-wallet/Engine API probes | Real faults/messages where observed, and **labeled simulated/adversarial client input** where crafted. No fake "independent nodes" or fake SLA readings |
| E — scientific decentralization acceptance | Additional genuinely independently administered host(s)/operator(s) only **if actually available** | Independently signed/activated validators, monitors in distinct administrative/fault domains, verified quorum and payouts | If not available, **mark independent-administrator/Byzantine-quorum acceptance NOT MET**, even when stage A–D work |

**Do not require an invented 4-VM or 64-validator experiment.** The number of Genesis validators is finite but chosen transparently from actual resources, actual Beacon protocol minimums and fault assumptions. One laptop is only one external machine; it may run one or multiple roles but cannot become several independent administrative domains. More than one validator key per operator can produce real PoS attestations, but does not add physical decentralization. A local unit test using four identities is **not** a claim of four live independent actors. A quorum requiring too many independent candidates must stay **unavailable/inconclusive**, never lower security by silently pretending same-owner keys are independent.

PoS finality needs sufficient actual active stake: for example a two-equal-operator stake system would lose >2/3 availability if one operator goes offline. Record exact active stake fractions rather than claiming fault tolerance from node count or from one laptop peer.

No static public IPv4 is a join requirement. At least some independently replaceable peers must be publicly reachable by native TCP/UDP; DDNS alone cannot traverse CGNAT. No Tailscale approval or mandatory private overlay. Public per-node HTTPS UI may use independently chosen transport/relay but must not become a central network admission service.

## Adversarial participants: what they may attack and what must reject them

All public nodes are untrusted. A participant may be a valid network peer but has **zero authority to modify another host's local configuration, consensus history, keys, lease records or monitor evidence** merely because it joined P2P. Cross-role permissions are per **actual on-chain identity and lease**, not per UI role label.

| Attack using real or crafted malicious-node/dashboard input | Prevention boundary and observed proof needed |
|---|---|
| Random peer uses public UI to switch validator/monitor/provider roles on another node | Owner-authenticated session with CSRF/origin protection; local-only role preferences do not give on-chain eligibility; never accept remote control commands |
| Public UI tries to override consensus genesis/finalized blocks, committee membership, precommitted q, monitor election seed or SLA verdict | No such global dashboard API, no owner escape hatch; exact genesis/chain IDs and immutable election/lease commitments enforced by clients + contracts |
| Invalid monitor submits fake vote, votes for another lease, duplicates, omits evidence or impersonates another signer | Contract membership and EIP-712 verification, nonces, domain+chain and lease/epoch binding, unique seat count and actual evidence interpretation; conflicting/insufficient accepted evidence remains unresolved |
| Provider/consumer manufactures a successful SLA without real receipt/observation | Signed message and immutable request/response hashes, real provider work and probe observations, explicit world-soundness assumptions; preserve indistinguishable `N,F,S` contractual histories |
| Cross-wallet withdrawal, wrong beneficiary, replay of settlement payout | Only sender's earned credit, immutable contract recipient, server-side local wallet binding and fresh transaction consent; on-chain checks are authoritative, not UI JavaScript |
| Uploaded lease/compute profile tries arbitrary shell, Python, Docker socket, host filesystem, privileged containers, secret mounts or direct validator key-manager | Strict allowlisted workload schema, hash-pinned image, bounded CPU/RAM/PIDs, non-root/no-new-privileges/cap-drop, localhost-only worker port binding and no Docker socket in any remote route |
| Public RPC access is used to obtain Engine JWT, key-manager keys, validator slashing DB, local owner password or developer deploy-key | Bind signer/Engine/key-management to restricted local/private interface; independent access controls, no debug/admin endpoints, no wallet secrets in HTML, logs, URLs or runtime ENV shown to clients |
| Malicious node floods CPU, RPC, monitoring or login endpoints | Per-peer/request size, concurrency, CPU/memory/time and gas limits, account-level and IP-level rate controls where feasible; authenticated paid workloads; protect signer priority; log **actual** load rather than invented TPS |
| Sybil monitor pool floods with worthless bonded TEST ETH accounts, biases random selection or controls a quorum | Declare economic/fault-domain assumptions, fair frozen candidate snapshot, independently checked sampling, possible weighted/stake concentration analysis; **cannot claim Sybil resistance from addresses or free TEST ETH alone** |
| Byzantine/unavailable monitors cause irreconcilable votes or liveness loss | Use precommitted finite per-lease `n,q,b` satisfying `2q-n>b`, `q<=n-b` under stated assumptions; if independent quorum unavailable, mark inconclusive and retain exposure under SSE—not arbitrary payout/slash |
| DNS/release mirror returns changed Genesis or malicious binary | Verify public source and SHA256 signatures/digests, reject conflicting chain identity and unsigned changes, independently replaceable mirrors; no coordinator accepting and approving joins |
| Validator client signs conflicting attestations or proposer manipulates time/entropy | Real CL slashing protection DB, independent BLS signer custody, genesis/fork domain binding; no V1 single privileged VRF authority or proposer-controlled entropy represented as secure randomness |

**Current code findings:**
- `services/provider-agent/compute_http_service.py` binds `0.0.0.0:8877` *inside the sandbox container*. The owner Docker launch adapter `tools/sse_docker_sla_runner.py` publishes that endpoint on **host loopback only** via `--publish 127.0.0.1:<port>:8877`, with CPU/memory/pids/read-only/cap restrictions. This guard must NEVER be widened to `0.0.0.0:<host-port>` for Internet callers.
- `services/provider-agent/direct_work_service.py` binds `127.0.0.1`, validates signed work requests against pinned chain state, enforces bounded body sizes and durable replay journal when served; legacy Tailscale service language is **not a final public network architecture**.
- `services/provider-agent/signed_http_service.py` and monitor service still have research-only key-in-environment patterns and loopback-only assumptions. These are NOT production-safe remote Internet key/role/monitoring deployments without review.
- **No deployed per-node public HTTPS owner dashboard is in the current mainline.** `tools/sse_node_dashboard_policy.py` is a **standalone candidate server-side authorization matrix** and `tests/test_sse_node_dashboard_policy.py` contains *adversarial unit fixtures*; passing them will NOT establish full web security or actual API integration. The final HTTP server must independently establish origin, CSRF, authenticated local owner, pinned chain, lease and signer evidence from trusted sources, not trust flags in user JSON. Even an owner is not a network administrator.
- Current live `OpenMonitorCommittee.sol` and `SSESettlement.sol` still implement legacy 4/3 committee and require actual dynamic committee migration (#38). Pure `AdaptiveMonitorQuorum.sol` tests passed 10/10 on VM, but are math only.

## Minimum evidence for each research claim

Record observed VM/laptop host identity, CPU/RAM/disk and infrastructure owner honestly, immutable Git revision, EL/CL/client image digests, network paths, packet reachability, actual beacon finality/slot, validator activation or lack thereof, transaction receipts/gas, raw sampled request-response/evidence files with privacy redaction, contract escrow balances before/after, actual workload CPU/RAM consumption, and failed attempts/attack response codes. Save no mnemonic/private keys and do not upload keystores, JWTs, secret ENV or raw personal data.

Separate result labels: **source unit test**, **local simulated adversarial input**, **real single-host execution**, **real VM↔laptop P2P**, **real multi-host execution**, **independent administrative operators**, **public Internet permissionlessness**. Never roll them all into one "decentralized system validated" statement.

**Remaining engineering:** review/lock consistent EL+CL genesis with real independent BLS custody; deploy genuine PoS chain31340; audit and integrate adaptive committee/escrow/VRF paths; actual public node installer and HTTPS console authenticated by host owner; live network and workload tests. Old chain31339 cannot be published. GitHub PRs remain draft/unmerged until their actual scope has passed evidence gates.
