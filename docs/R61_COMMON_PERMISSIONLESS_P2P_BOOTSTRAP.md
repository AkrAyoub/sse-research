# R61 — common permissionless native P2P bootstrap and no-private-LAN acceptance

**Date:** 2026-11-21. **Binding operator decision:** VM4706 original chain, VM4707 nonsigning peer, WSL laptop and all future participants must use the same Internet-capable transport + native Ethereum discovery pathway. **NO private provider LAN for native blockchain peering or bootstrapping, even temporarily.** This supersedes all older "first synchronize over cloud private LAN" suggestions. Source in feature PR #35; no new P2P or native consensus change has been executed on any VM by this document.

## Fixed chain identity, open transport and peer equality

- **Canonical original chain:** existing exact VM4706 chain31340 execution genesis and Beacon genesis, worthless TEST ETH, official Besu EL / Lighthouse Beacon and validator. Never create a second genesis or duplicate original validator signing key. Non-signing full node needs no test ETH.
- **Transport layer (provisional):** a full node joins the same openly joinable controllerless ZeroTier network `ff2328775f000000` and receives its own 6plane IPv6 under `fca0::/16`; no static IP, cloud tenancy, invitation, private GitHub account, or original owner SSH is required by *the transport itself*. This initial concrete overlay is the **same for every full node**, regardless of whether it also runs a validator, provider, consumer or monitor role. Any operator may optionally support more public direct/redundant transports once client compatibility is proven; no participant must use a special genesis-owner-only link.
- **Ethereum P2P (separate from overlay):** Besu native devp2p/discv4 or discv5 on the execution layer **AND** Lighthouse discv5/libp2p gossip/QUIC on the consensus layer, over reachable signed/adverted actual IPv6 peer identities. Correct chain genesis/fork is mandatory. Signed EL/CL ENRs and public peer record files must be independently rehostable, and every full node can be a discovery peer—not a permanent two-node whitelist. Peers not known at genesis can connect and sync by the same protocol. DNS or ENR publishers are hints, not authorization.
- **Blockchain/economic roles:** all nodes have the same *network support*, but role-dependent crypto/ports/transaction eligibility differ. Consumers/providers/monitors use signed/well-authenticated Internet-reachable application endpoints; validators also need a local signing client and correct protocol deposits. No fixed count of machines, roles or allowed nodes.

## No provider-LAN path: how to test honestly

Do not advertise or accept any `10.50.56.2`, `10.50.56.8`, `10.50.56.0/24`, `192.168.0.0/16` or other provider-private address as a native Besu/Lighthouse bootstrap ENR. Do not place a private-LAN peer in the acceptance set. Avoid server networking configurations that silently use provider LAN instead of the open network.

**Important:** An overlay IP `fca0:...` is virtual: ZeroTier may route its UDP encapsulation directly over the provider's private underlay if both VMs share infrastructure. **Peer applications sending to overlay IPv6 alone are not proof of no private LAN underlay.** Before claiming the user requirement is fulfilled, measure native P2P with a host that is not on the provider network (e.g. actual WSL laptop) and inspect any provider-private direct paths; choose independent external operators/networks for resilience. Without such measurements mark underlay independence `NOT PROVEN`. Do not change host firewall/routing to suppress direct paths without separately reviewing management access and signing-host recoverability.

## Public onboarding UX still pending

The final role-neutral installer must obtain a publicly available signed/hash-pinned source/genesis release from redundant mirrors, install the shared networking transport once under local OS consent, install the verified real EL/CL clients, create role-local identities and manage services with network readiness/restart ordering.
