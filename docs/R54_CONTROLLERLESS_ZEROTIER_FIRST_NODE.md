## Upstream evidence and precise ad-hoc ID

ZeroTier documentation https://docs.zerotier.com/protocol/ (November 2026) specifies special ad-hoc ffSSSSEEEE000000 public controllerless networks with locally generated membership credentials, no approval or central network controller; IPv6 unicast TCP/UDP ONLY, no multicast/broadcast, 6plane NDP-emulated addresses. The port range is inclusive and filters destination UDP packets and incoming TCP SYN. Network ff2328775f000000 has SSSS=0x2328=9000, EEEE=0x765f=30303. This contains Lighthouse libp2p TCP9000/discv5 UDP9000/QUIC UDP9001, Besu devp2p TCP30303/discv5 UDP30303. It excludes SSH TCP22, HTTP API 5052, ENGINE API 8551, and ALL host services below9000 from the overlay. Some other services 9000..30303 are reachable if bound to IPv6 and not further firewalled; only publish reviewed P2P services. Ad-hoc network ID is defined by port RANGE not a unique project namespace, so other people may use the same network ID. Secure Ethereum chain identity and authenticated signed ENRs, peer IDs and EVM/Beacon genesis must remain independent of this transport.

ZeroTier infrastructure is still partially centralized in planetary roots/relays (https://docs.zerotier.com/protocol/). Thus open join no ZeroTier Central account is NOT end-to-end fully trustless networking. Unlike Pinggy free trial, ZeroTier doesn't intentionally terminate sessions hourly; NAT failures, overlay root outages, firewall or service-version issues could still disrupt peer connectivity. Some incoming UDP response ports may fall OUTSIDE configured range; actual discv5/QUIC roundtrips must be tested before claiming suitability. Overlay traffic still counts as genuine TCP/UDP native clients but requires every joining peer to install ZeroTier automatically. Do not call this plain public-IP native Ethereum P2P.
